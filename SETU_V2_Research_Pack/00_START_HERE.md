# SETU V2 — Start Here

## The decision

Build a **source-first, offline-capable adaptive learning PWA**—not a hard-coded Algebra demo and not a chat box surrounded by decorative screens.

A student should be able to:
1. Choose a curriculum resource from a verified catalogue **or** upload a document they are entitled to use.
2. See what SETU actually extracted before trusting the course.
3. Confirm the class, subject, language, source scope and learning goal.
4. Review a proposed learning path, with uncertain or unreadable sections made visible.
5. Start with the first two or three validated lesson packs: explanation, takeaways, examples, appropriate diagrams/photos, practice, quiz and contextual doubts.
6. See later lessons generated by a durable background worker with honest per-lesson states.
7. Read and practise using selected downloaded content offline.
8. Save doubts offline, synchronise on reconnection and keep answer/source references available offline.
9. See lesson completion separately from evidence-based concept mastery.
10. Let teachers see useful evidence and guide students rather than being replaced by AI.

This extends the Code Kernel challenge. Its explicit centre is Classes 6–10, Indian classroom fit, adapting what/how/pace to student understanding, Learn/Solve/Test, usability for ages 11–16 and teacher empowerment. Upload-first, background generation, offline doubt queue and automatic reference imagery are SETU product choices, not verbatim contest requirements.

## Decisions that prevent another broken rebuild

### A resource is not a course
A PDF is a source. Ingest it, preserve page/section anchors, derive a candidate outline, validate it, then create versioned lesson packages that cite the source. Don't invent chapters from a filename.

### The LLM is not the database, grader or source of truth
Store documents, lesson packages, questions, answers, attempts, mastery evidence and generation state in explicit data models. The LLM drafts explanations and content; validators, source evidence, answer-key tests and learner-state policy decide what gets published and what happens next.

### Generate the first 2–3 lessons eagerly; enqueue the rest
The backend owns durable jobs. Don't rely on a long HTTP request, browser timer or in-process task that disappears on restart. A lesson is `Ready` only after source references, question/answer material and visual specifications validate.

### Offline is a first-class capability
Use a service worker for the app shell and IndexedDB for lesson packs, quiz data, local progress and doubt outbox. Don't rely on `localStorage` for the main data model. Background Sync is an enhancement only; also sync on app open/resume, focus, `online` and manual request.

### Discovery is not permission to rehost
A public PDF URL doesn't automatically allow SETU to mirror it, process it or package it offline. Store resource rights and allowed actions explicitly.

### Same credentials does not mean same app data
Reuse configured Supabase credentials only after verifying the target. Rebuild the app schema through migrations. Back up first; clear the intended SETU-owned tables/objects/test records, not Supabase-managed schemas. Never expose environment values.

## Recommended baseline

- Frontend: React + Vite + TypeScript + CSS Modules.
- Offline store: IndexedDB via Dexie or a justified alternative; service worker for the app shell.
- Backend: FastAPI, typed contracts and a durable worker process.
- Database: Supabase PostgreSQL; relational source/learning data plus Postgres full-text search and pgvector.
- Files: private Supabase Storage for user files and permitted assets.
- Models: backend provider adapter; hosted endpoint for deployed generation and optional LM Studio/local endpoint for development. No provider keys in browser.
- Tests: pytest, frontend tests, database/RLS tests and real browser end-to-end tests.

Don't add Redis, Celery, a second vector database or another object store merely because it sounds scalable. Add services when an observed requirement justifies the cost and operational burden.

## First vertical slice

`choose/upload → validate → extract pages → index → propose path → first 3 lessons ready → open lesson → answer practice → record evidence → queue doubt offline → reconnect → grounded answer with source → view saved lesson/answer offline`.

The code and data model must be source- and subject-agnostic. Synthetic fixtures belong in tests or isolated demo mode, not ordinary student routes.
